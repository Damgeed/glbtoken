Security Practices & Roadmap

Updated August 22, 2026 · 4 min read

GlbTOKEN is actively hardening its application and deployment. This page describes controls that are present in the public codebase and distinguishes them from planned work.

Certification status: GlbTOKEN does not currently claim independent SOC 2, ISO 27001, PCI DSS, HIPAA, or FedRAMP certification. No audit report should be inferred from this page. Organizations with formal compliance requirements should complete their own vendor review before using the service for regulated data.

Current application controls

  • Passwords are bcrypt-hashed; access and refresh credentials are time-limited, and refresh tokens are hashed in the database.
  • GlbTOKEN API keys are stored as one-way hashes. The full value is shown only when a key is created.
  • TOTP and webhook secrets are encrypted before database storage when persistent secret encryption is configured.
  • Payment credits require provider verification and use idempotency checks to reduce duplicate-credit risk.
  • Authentication, payment, key-management, and administrative routes are rate-limited and return no-store cache headers.
  • Outbound webhooks require HTTPS, reject private or reserved destinations, and revalidate redirect targets.
  • Users can enable TOTP two-factor authentication and one-time recovery codes.

Deployment responsibilities

Security depends on production configuration. Operators must use separate high-entropy values for JWT signing, database-secret encryption, and admin automation; configure verified payment webhooks; keep dependencies patched; back up the database; and restrict the origin so it is not directly reachable outside the Cloudflare path.

Known limitations and roadmap

  • Move browser refresh credentials from JavaScript-accessible storage to Secure, HttpOnly cookies with reuse detection.
  • Reserve estimated model cost atomically before an upstream request, then reconcile against reported usage.
  • Remove inline scripts and handlers so the site can enforce a nonce- or hash-based Content Security Policy without unsafe-inline.
  • Complete an independent penetration test and publish a coordinated vulnerability-disclosure policy.
  • Document retention periods and subprocessors before making formal privacy or compliance commitments.

If you discover a security issue, avoid including credentials or customer data in your message. Contact support@glbtoken.com with a concise reproduction and affected endpoint.
